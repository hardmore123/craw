# 零售线多国自动适配技术方案（网评 + 价格）

> 版本：v0.2（2026-09-17，P0 落地）
> 范围：零售站的**价格监控**与**网评采集**，目标覆盖墨西哥 / 加拿大 / 美国 / 欧洲等多国。
> 状态：**P0-1~P0-4 已落地**（RetailSpec 契约 + 校验 + match + shops + 导出动态化），
> P1（liverpool 反抽象）真实站跑通。
> 关联：`RetailSpec_schema规范.md`（契约）、`零售线效果指标与验收标准.md`（指标与任务表）、
> `README_整体思路.md`（SPEC 线整体思路，本方案沿用其"契约分离判断与执行"骨架）

---

## 1. 从日本线学到什么

### 1.1 日本线已经跑通的（可复用的资产）

| 能力 | 落地位置 | 复用价值 |
|---|---|---|
| **通用 20 列网评模板** | `review_export.COLUMNS` | ★跨国跨站已统一，直接复用 |
| **声明式抽取引擎** | `extract.py` 的 `Extractor` + `schema.json` | ★六段式 + transform 管道 + 多选择器兜底，成熟 |
| **四场景骨架** | `scenarios.py` s1~s4 | ★`s4_reviews` 的增量停止逻辑已实现 |
| **增量停止** | `s4_reviews`：已入库 `review_key` 集合，本页全已知即停 | ★零售线省请求的核心 |
| **型号匹配兜底链** | `SiteAdapter.find_product`：精确 → 主干 → **返回 None** | ★"宁缺毋滥"原则已确立 |
| **限速/反爬/缓存** | `infra.py` RateLimiter / BlockDetector / DiskCache | 直接复用 |

### 1.2 日本线的做法为什么不能直接搬到其它国家

这是本方案要解决的核心问题。三个基于代码事实的障碍：

**障碍一：kakaku 是"脚本 + 硬编码"模式，不是配置驱动**

`sites/kakaku_jp/schema.json` 自己的注释写着：

> "评价抓取主要由 `scripts/crawl_kakaku_reviews.py` 用适配器方法完成；
> 此处仅登记锚点与关键选择器"

而 `KakakuJpAdapter` 有一批**站点专属方法**不在通用契约里：
`review_url(page)`、`bbs_url`、`shop_prices()`、`map_shop_columns()`、
`bbs_threads(with_meta)`、`release_text()`、`size_inch()`。
`crawl_kakaku_reviews.py` 约 1250 行。

→ **换一个国家等于重写一遍脚本**，这正是人工成本所在。

**障碍二：价格表的店铺列是日本硬编码**

`price_export.py`：
```
COLUMNS = FIXED_HEAD + SHOP_COLUMN_NAMES + FIXED_TAIL
```
`SHOP_COLUMN_NAMES` 是 8 个日本店铺（ヨドバシ.com / エディオン 等），
由 `KakakuJpAdapter.SHOP_COLUMNS` 和 `map_shop_columns()` 配套。

→ 墨西哥直接复用会产出**8 列全空**的无意义表。

**障碍三：kakaku 是"聚合站"，多数其它国家是"自营站"**

kakaku 一个商品页列多家店铺报价（`shop_prices()` 返回 `{店铺名: 价}`）；
Amazon/Liverpool/Best Buy 是自营，一个页面一个价。两种结构的价格模型不同。

### 1.3 已有的多国零售站适配器（现状盘点）

`overseas/sites/` 下已有一批零售站：`amazon_ca/mx/us`、`bestbuy_ca/us`、
`walmart_ca/mx/us`、`costco_ca/us`、`liverpool_mx`、`coppel_mx`、`sams_mx`、
`palacio_mx`、`canadiantire_ca`、`leons_ca`、`thebrick_ca`、`visions_ca` 等。

其中**带 `schema.json` 的是声明式**（amazon_*、walmart_mx/us、bestbuy_us、
costco_us、liverpool_mx、coppel_mx、sams_mx、palacio_mx、generic_jsonld），
**只有 adapter.py 的是硬编码**（bestbuy_ca、canadiantire_ca、leons_ca、
thebrick_ca、visions_ca、各品牌官网站）。

→ **声明式的那批就是自动化的模板**，说明这条路本身走得通；
要做的是把"人工写 schema.json"变成"自动生成 + 校验"。

## 2. 核心思路：沿用 SPEC 线骨架，换一套契约

SPEC 线已验证的骨架：**用 JSON 契约把"每站不同的判断"与"固定的执行"分开**。
零售线沿用同一骨架，但契约换成 `RetailSpec`（原因见规范 §0.2）。

```
                ┌──── 入口 A：skill（人机协同，判断力优先）────┐
                │   .kiro/skills/retail-schema-gen/           │
                └──────────────────┬──────────────────────────┘
                                   │
   Probe ──────► Generate ──────► Verify ──────► Execute
   探测结构       产出 RetailSpec   三层校验        场景层执行
   retail_probe   智能体 / LLM      静态+实测+抽检   s1~s4 + 导出
                                   │
                ┌──────────────────┴──────────────────────────┐
                │  入口 B：程序化 CLI（无人值守，可定时）       │
                │  overseas.cli retail-onboard                │
                └─────────────────────────────────────────────┘

日常重跑：读已存 RetailSpec → 场景层执行 → 导出（零 LLM）
```

### 2.1 四段在零售线的具体含义

| 段 | 零售线要做的事 | 与 SPEC 线的差别 |
|---|---|---|
| **Probe** | 拿一个**已知型号**去站内搜索，探测：搜索结果容器/商品页锚点/价格区/评价区/翻页方式/是否多店铺 | SPEC 线探"型号列表页"，零售线探"搜索→商品页→评价页"三类页面 |
| **Generate** | 产出 RetailSpec（含 `match` / `paginate` / `incremental` / `shops`） | 多了型号匹配与增量段 |
| **Verify** | ★三层：静态合法 + 真实页面命中 + **匹配准确率抽检** | SPEC 线看找全率，零售线看**匹配准确率**（防张冠李戴） |
| **Execute** | 复用 `scenarios.py` 的 s2（价格监控）/ s4（评价增量） | 已有，主要改造点是让它们读 RetailSpec 而非硬编码 |

### 2.2 四条不可动摇的原则（继承 SPEC 线）

| 原则 | 零售线的具体落地 |
|---|---|
| **只产配置，不产代码** | RetailSpec 是纯 JSON；需要 JS 交互只能引用已登记片段库 |
| **审计即 reward** | 用真实入库数据算匹配率/填充率，不看 LLM 自述 |
| **红线硬否决** | ★`match.on_no_match` 必须 `skip`；匹配准确率 < 阈值直接判失败 |
| **能力边界显式化** | schema 枚举值必须在引擎白名单内，越界报错不静默降级 |

> 零售线的红线与 SPEC 线**不同**：SPEC 线怕"抓不全"，零售线怕"**抓错**"。
> 一条 55 寸的价格记到 65 寸头上，或把支架评价当电视评价，
> 这种污染比缺数据更难发现、危害更大。

## 3. 关键设计决策

### 3.1 型号匹配：三段兜底 + 宁缺毋滥

复用 `SiteAdapter.find_product` 已确立的逻辑，配置化为 `match` 段：

```
站内搜索(keyword_template) → 取 candidate_limit 个候选
  ↓
① 精确：型号归一化后完整出现在 sku/title 中 → 命中
  ↓ 不中
② 主干：去前导尺寸与 pro/max 尾缀后的主干出现 → 命中
  ↓ 不中
③ 返回 None（skip），记一条"未匹配"审计
```

**排除规则**（`match.reject`）与匹配同等重要：墨西哥站搜 "Hisense 55U6N"
会返回支架（soporte）、遥控器（control remoto）、保护套（funda），
必须靠 `title_contains_any` / `url_contains_any` 排掉。

### 3.2 多店铺 vs 自营：`shops.mode` 分流

| mode | 适用 | 价格模型 | 导出列 |
|---|---|---|---|
| `multi_shop` | kakaku 型聚合站 | 一个型号 N 个店铺价 + 最低价 | `shops.columns` 声明的店铺列 |
| `single_shop` | Amazon/Liverpool 等自营 | 一个型号一个价 | 简化列（渠道即店铺） |

**必须改造 `price_export.py`**：从读模块常量 `SHOP_COLUMN_NAMES`
改为读 spec 的 `shops.columns`，否则跨国无法出表（P0-3）。

### 3.3 评价增量：复用已有逻辑，配置化停止条件

`s4_reviews` 已实现"已知 key 集合 + 本页全已知即停"。
本方案只把停止条件配置化（`incremental.stop_when`），并强调
`review_key` 必须用站点稳定 ID——用"标题+作者"拼的伪 key 会重复入库。

### 3.4 币种与促销价

零售线特有风险，`price` 段已有 `transform` 支持（`money` / `currency_mx` /
`currency` 等，见 `extract.py` 的 `_CUR_PATTERNS`）：

| 风险 | 处理 |
|---|---|
| 裸 `$` 歧义（MXN vs USD） | 按站点用 `currency_mx` 之类的地区专用 transform；spec 顶层 `currency` 兜底 |
| 促销价 vs 原价 | `price`=现售价，`list_price`=划线价，分开抽 |
| 会员价/多价并存 | `price.selectors` 顺序即优先级，第一个非空采用 |
| 缺货页无价 | `in_stock` 抽取 + 允许 price 为空，不当失败 |

## 4. 与 SPEC 线的复用与隔离

| 组件 | 处理 |
|---|---|
| `Extractor` / `load_schema` / transform | **完全复用**，零售 schema 本来就走它 |
| `infra`（限速/反爬/缓存）、`fetchers` | **完全复用** |
| `scenarios` s1~s4 | **复用 + 小改**（读 RetailSpec） |
| `review_export` 20 列模板 | **完全复用** |
| `price_export` | ★**需改造**（店铺列动态化） |
| `spec_probe` / `spec_generator` / `generic_spec` | **不复用**，零售线新建 `retail_probe` / `retail_generator` |
| AdapterSpec 三个白名单常量 | **不复用**，零售线新建自己的白名单 |

**隔离理由**：两条线的 Probe 探测对象、Verify 判据、执行场景都不同，
强行共用一套 generator 会让 prompt 与校验逻辑互相污染。
共用的是**更底层的抽取与基础设施**，那部分本来就是共享的。

## 5. 分阶段落地

| 阶段 | 内容 | 用 LLM | 价值 | 风险 |
|---|---|---|---|---|
| **一** | `price_export` 店铺列动态化 + RetailSpec 加载/校验 | 否 | 解开跨国死结，拿确定性收益 | 低 |
| **二** | 把 1 个已有声明式站（liverpool_mx）反抽象成 RetailSpec，跑出与现状一致的结果 | 否 | 验证配置驱动可行，打地基 | 低 |
| **三** | 接 Probe + LLM/智能体生成 RetailSpec，在**已知好抓的站**上试 | 是 | 验证闭环收敛 | 中 |
| **四** | 扩到新国家新站，保留"不收敛转人工" | 是 | 实现目标 | 中高 |

**强烈建议从阶段一起步**——它不依赖 LLM，且是后面所有阶段的前提
（店铺列不动态化，墨西哥连表都出不了）。

## 6. 风险与边界（务实说明）

### 6.1 技术风险

| 风险 | 表现 | 缓解 | 残留 |
|---|---|---|---|
| **型号匹配错**（最高危） | 价格/评价张冠李戴 | 三段兜底 + reject 规则 + `on_no_match=skip` + 抽检指标 | 同系列不同尺寸仍可能混，需人工抽检 |
| 反爬 | Amazon/Walmart 强风控、验证码 | 限速 + 浏览器指纹 + 命中即标记 | 部分站根本抓不了 |
| 评价语言多样 | 西语/法语/葡语评价，AI 提炼质量下降 | 复用现有翻译层（`translator.py`/`review_translation.py`） | 小语种质量待验证 |
| 促销期价格跳变 | 黑五价被当常态价 | 价格是时序快照，保留 `captured_at`；不做均值 | 需下游解读 |
| 评价排序不稳 | 增量停止误判"已抓完" | `stop_when=n_pages_no_new` 放宽 | 极端情况仍可能漏 |
| DOM 改版 | 选择器失效 | 多选择器兜底 + 定期 health 探测 | 改版当天到探测之间有缺口 |

### 6.2 明确做不到 / 不做

- **不追求任意零售站零人工**。强反爬站（部分 Amazon 地区）、需登录站、
  验证码站仍需人工或放弃。
- **不做跨站价格比对的业务判断**，只提供带 `captured_at` 的时序快照。
- **不保证评价全量**。评价常有平台限流（只放前 N 页），我们抓可见部分并如实标注。
- **不自动处理需登录/加购才显示的价格**。

### 6.3 合规

零售站的 robots/ToS 比品牌官网更严格。**必须有站点白名单准入**，
不是给个 URL 就抓。这条在 SPEC 线是 P2，在零售线应提到 **P1**。

## 7. 一句话结论

日本线证明了"声明式抽取 + 增量停止 + 20 列模板"这套零售能力是可行的，
但它**卡在三处硬编码**（脚本化的 kakaku 流程、日本店铺列、聚合站假设）。
本方案用 `RetailSpec` 把这三处配置化，沿用 SPEC 线已验证的四段流水线与双入口，
**先做不依赖 LLM 的阶段一（店铺列动态化）拿确定性收益**，再逐步引入自动生成。

零售线最该警惕的不是抓不到，而是**型号匹配错导致的数据污染**——
所以 `on_no_match=skip` 和匹配准确率抽检是不可省的红线。
