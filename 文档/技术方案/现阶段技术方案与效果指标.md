# 现阶段技术方案与效果评价指标

> 版本：v1.0（2026-09-16）
> 适用范围：品牌官网 **SPEC（规格）抓取线**。价格/网评零售线不在本方案内。
> 关联文档：`AdapterSpec_schema规范.md`（契约）、
> `方案对比_skill化schema生成_可行性报告.md`（路线判断）、
> `LLM自动适配器技术方案.md`（历史全过程）

## 第一部分：现阶段技术方案

### 1. 一句话定位

把"接入一个新电视站"从**写 300~500 行 Python 适配器**，降级为
**给一个 URL + 审一份 JSON 配置**；日常重跑零 LLM 依赖。

### 2. 架构：四段流水线 + 双入口

```
                    ┌──────────── 接新站 / 疑难诊断 ────────────┐
                    │  入口 A：skill（人机协同，判断力优先）      │
                    │  .kiro/skills/spec-schema-gen/            │
                    └───────────────┬───────────────────────────┘
                                    │
   Probe ──────► Generate ──────► Verify ──────► Execute
   探测结构      产出 schema       双层校验       引擎抓全站
   spec_probe    (智能体 / LLM)   validate +     generic_spec
                                  score_on_html
                                    │
                    ┌───────────────┴───────────────────────────┐
                    │  入口 B：程序化 CLI（无人值守，可 CI）      │
                    │  overseas.cli spec-onboard                │
                    └───────────────────────────────────────────┘

日常重跑：读已存 schema → 引擎全量抓 → 导出（完全不调 LLM）
```

**两个入口共用**同一份 schema 格式、同一套校验、同一个执行引擎。
差别只在 Generate 那一环由谁来做。

### 3. 各段职责与落地位置

| 段 | 做什么 | 代码 | 状态 |
|---|---|---|---|
| **Probe** | 打开入口页，排名产品链接选择器（按型号纯度）、归纳 URL 模式、判分页方式 | `overseas/spec_probe.py` | ✅ 多站验证 |
| **Generate** | 据探测信号产出 AdapterSpec | 入口A：skill<br>入口B：`spec_generator.py` | ✅ 双入口 |
| **Verify** | 静态校验 + 真实页面实测打分（含找全率否决） | `spec_generator.validate_spec` / `score_spec_on_html` | ✅ |
| **Execute** | 按 schema 发现型号 + 逐型号抓规格 + 审计入库 | `overseas/generic_spec.py` | ✅ 单层结构 |

### 4. 核心设计原则（不可动摇的四条）

| 原则 | 落地方式 | 防的是什么 |
|---|---|---|
| **只产配置，不产代码** | 需执行 JS 只能 `snippet_ref` 引用已登记片段库 | 失控/恶意逻辑；坏配置最多抓不到 |
| **审计表即 reward 函数** | 用真实入库数据打分，不看 LLM 自述 | 闭环"自我感觉良好" |
| **找全率硬否决** | `expected.model_count` 对比，< 80% 直接判失败 | ★**抓了一半当成功**（最危险） |
| **能力边界显式化** | 三个白名单常量；越界 `NotImplementedError` 而非静默降级 | 假装支持导致的隐性数据缺失 |

> 第三条是本方案的红线。技术方案 §9.3 明确：**误判成功比抓不到更糟**，
> 因为它污染交付数据且难被发现。

### 5. 当前能力边界（截至 2026-09-16）

```
discover.mode        : dom_anchor                                （1 种）
paginate.snippet_ref : numbered_pages_generic, philips_paginate  （2 个）
extract_order        : embedded_json, embedded_json_philips,
                       generic_spec_js                           （3 种）
series_rule          : strip_leading_size                        （1 种）
```

**能全自动覆盖的结构**（4 类，均已真实站验证）：

| 结构型 | 验证站点 | 结果 |
|---|---|---|
| 静态 lineup 一次列全 | 秘鲁 Hisense | 13 系列 36 型号 |
| 懒加载注入 | REGZA JP | 39 系列 39 型号 |
| JS 延迟注入 | Sony BRAVIA JP | 8/8 在售 |
| 编号页码分页（含替换式） | Philips CA | 11 系列 **25/25 = 100%** |

**明确做不到的**（记为 P0 缺口，不假装支持）：

| 缺口 | 影响站点 | 优先级 |
|---|---|---|
| 多级发现（总览→系列→型号） | 松下、夏普 | P0-1 |
| `xhr_api` 接口发现 | TCL、Samsung、LG | P0-2 |
| `query_param` 分页（`?firstResult=N`） | LG | P0-3 |
| 点 tab 展开才出规格 | TCL 类 SPA | P1 |

### 6. skill 入口的构成

```
.kiro/skills/spec-schema-gen/
    SKILL.md          主流程（Step 0 查经验 → 1 探入口 → 2 探型号页
                      → 3 写 schema → 4 验证 → 5 诊断 → 6 强制沉淀）
    probe.py          强探测脚本（--entry / --model / --verify）
    reference.md      判断经验库（8 节，全部来自真实站教训）
    cases.jsonl       案例库（5 个已实测站，可 grep 匹配相似站）
    playbook/         7 类结构型套路 + 索引
```

设计要点：

- **经验闭环**：Step 0 先查案例库（新站十有八九和做过的同型），
  Step 6 强制回写。这是 skill 越用越强的唯一机制。
- **复用而非重写**：`probe.py` 内部调 `spec_probe.probe_site` + `BrowserFetcher`，
  校验调 `validate_spec` / `score_spec_on_html`，抓取调 `spec-crawl --schema`。
- **止损前置**：`playbook/needs_handwritten.md` 给出 5 个止损信号，
  避免在超边界站上耗时间。

### 7. 分工原则

| 场景 | 用哪个入口 | 理由 |
|---|---|---|
| 接入新站 | skill | 判断力强，能处理没预料到的结构 |
| 疑难诊断（抓不全、改版失效） | skill | 能自主迭代试选择器 |
| 改版自愈 / 定时健康探测 | 程序化 CLI | 必须无人值守（skill 需人开 IDE） |
| 日常重跑 | 都不用 | 读已存 schema，零 LLM |

## 第二部分：效果评价指标

指标分四层。**L1 是红线（不达标即不可交付），L2 是核心业务价值，
L3 是效率收益，L4 是系统健康度。**

### L1 — 数据正确性（红线，一票否决）

| 指标 | 定义 | 阈值 | 当前 | 采集方式 |
|---|---|---|---|---|
| **找全率** | 落库型号数 / 官网标称型号数 | **≥ 95%** 可交付<br>≥ 80% 可继续调<br>< 80% 判失败 | Philips 100%<br>REGZA 100%<br>秘鲁 100% | `score_spec_on_html` + 实抓审计 |
| **守恒率** | 落库型号数 / 入口发现型号数 | **= 100%** | 待补测 | 对比 `spec_entry_audit` 与 `spec_series_status` |
| **误判成功率** | 标 success 但实际找全率 < 95% 的站占比 | **= 0** | 0（5 站） | 人工抽查 `cases.jsonl` |
| **规格非空率** | 规格行中键值均非空的比例 | ≥ 60% | 未系统测量 | ⚠️ Verify L3 层待补 |
| **规格行数** | 每型号抓到的规格条目数 | ≥ 8 行 | Philips 约 60 行 | `spec-crawl` 输出 |

> **守恒率**是防 Samsung 那类"同名系列覆盖、看着齐了其实少了"的隐蔽 bug。
> 当前只在 Philips 验证过一致，需补全量二次审计。

### L2 — 覆盖面（核心业务价值）

| 指标 | 定义 | 目标 | 当前 |
|---|---|---|---|
| **全自动站点数** | 无需手写适配器即可抓全的站 | 阶段目标 10 站 | **4 站**（Philips CA、REGZA、秘鲁 Hisense、Sony JP） |
| **结构型覆盖数** | 支持的页面结构类别 | 7 类 | **4 类** |
| **站点自动化率** | 全自动站 / 目标站总数 | ≥ 60% | 4 / 至少 10 ≈ 40% |
| **P0 缺口数** | 已识别未实现的引擎能力档位 | 收敛到 0 | **3 个**（多级 / xhr_api / query_param） |

> 覆盖面**只能靠扩引擎档位**提升，skill 化不会自动带来覆盖面增长
> （详见可行性报告 §2.3 约束二）。

### L3 — 效率收益（投入产出）

| 指标 | 定义 | 目标 | 基线（手写） |
|---|---|---|---|
| **接站耗时** | 从拿到 URL 到 schema 达标 | ≤ 2 小时 | 手写 1~3 天 |
| **接站代码量** | 新站需写的 Python 行数 | **0 行**（纯配置） | 224~502 行 |
| **一次通过率** | 首轮 Generate 即通过校验的站占比 | ≥ 50% | Philips 需 1 轮修复 |
| **修复轮次** | 达标前的平均调整轮数 | ≤ 3 轮 | Philips 2 轮、Sony 2 轮 |
| **日常重跑 LLM 成本** | 每次全量抓取的 token 消耗 | **0** | 0 ✅ 已达成 |

手写适配器行数基线（实测）：

| 站点 | 行数 |
|---|---|
| samsung_mx | 502 |
| samsung_us | 376 |
| tcl_us | 374 |
| lg_ca | 277 |
| philips_ca | 224 |

### L4 — 系统健康度（生产化程度）

| 指标 | 定义 | 目标 | 当前 |
|---|---|---|---|
| **schema 持久化率** | 入库 `adapter_spec` 表的 schema 占比 | 100% | **0%** ⚠️ 表未落地，schema 存 JSON 文件 |
| **改版检出时延** | 站点改版到系统发现的时间 | ≤ 7 天 | **不可测** ⚠️ `spec-health` 未实现 |
| **审核门覆盖率** | 经 candidate→approved 流转的 schema | 100% | **0%** ⚠️ 未实现，当前生成即用 |
| **失败现场留档率** | 失败站点保留完整探测现场的比例 | 100% | 部分（`data/probe/` 有 HTML，无结构化 `onboard_run`） |
| **经验回写率** | 完成后回写 `cases.jsonl` 的任务占比 | 100% | 新机制，待观察 |
| **合规准入** | 抓取前过白名单/robots 检查 | 100% | **0%** ⚠️ 未实现 |

> L4 四项标 ⚠️ 的是 P1 生产化缺口。**它们不影响"能不能抓"，但影响"能不能无人值守"。**

### 指标看板（当前快照）

```
L1 数据正确性   ███████░░░  70%  找全率/守恒已验证，规格质量校验待补
L2 覆盖面       ████░░░░░░  40%  4/10 站，4/7 结构型，3 个 P0 缺口
L3 效率收益     ████████░░  80%  0 代码量已达成，接站耗时待多站验证
L4 系统健康度   ██░░░░░░░░  20%  库表/health/审核门/合规 均未落地
────────────────────────────────────────────────
综合完成度      ██████░░░░  约 55%（生产化视角）
                             发现阶段 POC 视角约 70%
```

> 两个百分比不矛盾：POC 目标（证明配置驱动可行）已达 70%，
> 但按生产级标准（无人值守、可自愈、合规）算约 55%。

## 第三部分：验收方式

### 单站验收清单

新接一个站，按序全过才算达标：

```powershell
# 1. 静态校验 + 实测打分（两层都要 passed）
py -3.12 .kiro/skills/spec-schema-gen/probe.py --verify data/schema_drafts/<code>.spec.json

# 2. 真实抓取（独立 sandbox，别污染正式库）
$env:OVERSEAS_DB = "data/sandbox_<code>.db"
py -3.12 -m overseas.cli spec-crawl --schema data/schema_drafts/<code>.spec.json
```

| 检查项 | 判据 |
|---|---|
| 静态校验 | `static_problems` 为空 |
| 实测打分 | `passed=true`，`score ≥ 70` |
| 找全率 | 落库型号数 / 官网标称 ≥ 95% |
| 守恒 | 发现数 == 落库数 |
| 规格质量 | 抽 3 个型号，每个 ≥ 8 行规格，键值非空 |
| 回归不破坏 | Philips CA 仍 11 系列 25 型号 |
| 经验沉淀 | `cases.jsonl` 已追加一条 |

### 回归基线（任何改动后必跑）

| 站点 | 期望结果 |
|---|---|
| Philips CA | 系列 11，型号 25，终态 stable，ok=11 fail=0 |
| REGZA JP | 39 系列 39 型号 |
| 秘鲁 Hisense | 13 系列 36 型号 |
| Sony BRAVIA JP | 8 型号（且**无** `discover.paginate`） |

## 第四部分：下一步优先级

| 优先级 | 工作 | 提升哪个指标 | 预期效果 |
|---|---|---|---|
| **P0-1** | 多级发现（松下/夏普验证） | L2 覆盖面 | 全自动站 4→6，结构型 4→5 |
| **P0-2** | `xhr_api` 接口发现 | L2 + L1 | 覆盖 TCL/Samsung/LG；接口路径找全率更可靠 |
| **P0-3** | `query_param` 分页 | L2 | 覆盖 LG |
| **P1-1** | `adapter_spec` / `onboard_run` 库表 | L4 持久化 | 解锁版本回滚、失败复现 |
| **P1-2** | `spec-health` 定期探测 | L4 改版检出 | 从"不可测"到 ≤7 天 |
| **P1-3** | Verify L3 规格质量实测 | L1 规格非空率 | 补上唯一未系统测量的红线指标 |
| **P2** | 合规白名单准入 | L4 合规 | 从 0 到 100% |

**建议先做 P0-1**：边界最明显，且 skill 已备好 `playbook/multilevel.md`
上报指南，缺口定义清晰可直接开工。
